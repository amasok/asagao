# ADR 0009: 入り口の読み取りは app.Query を通し、ポートは QueryStore 1 つにする

- 状態: 提案 (Issue #11 の段階 c2)
- 日付: 2026-11-17
- ADR 0003 の決めたことの 5 (読み取りは段階 c までは入り口から store を直接呼んでよい) の、段階 c のあとの形を決める

## 背景

- 段階 c2 で、読み取りの型 (表示の型、一覧の条件、エラーの値、文言) は `internal/readmodel` に移った。store の読み取りのメソッドの引数と戻り値は、readmodel と domain の型だけになった。
- 入り口は、store の読み取りのメソッドを約 30 種類呼んでいる (MCP 19 種類、CLI 23 種類、TUI 24 種類。重なりが多い)。書き込みと違い、読み取りには名前の解決や変換の手順がほとんどなく、入り口は store の答えをそのまま表示する。
- ADR 0008 で、「Go の習慣ではインターフェースは使う側に置く。使う側のないポートは作らない」とした。読み取りのインターフェースだけを app に置くと、使う側は入り口になってしまう。

## 決めたこと

1. **app に `Query` (読み取りのユースケース) を置き、そのポートとして `QueryStore` を 1 つ置く。** `Query` の各メソッドは、store の同じ名前のメソッドをそのまま呼ぶ。引数と戻り値は readmodel と domain の型だけ。`*store.Store` はそのまま `QueryStore` を満たす。
2. **ポートは分けない。** 書き込みは、ユースケースごとに使うメソッドが違うので、小さく分けた (a4・a6)。読み取りは `Query` 1 つが全部を使うので、分けても使う側は同じになる。メソッドは、タスク・人・プロジェクト・通知・キャッシュと outbox の順に、コメントで区切って並べる。
3. **書き込みの前に名前を解決するための読み取り (`ResolveSection` など) は、今までどおり書き込みのポートに置く。** 入り口が表示のために呼ぶもの (`ResolveProject`・`ResolveUser(s)`・`ResolveCustomField`) は、`QueryStore` にも置く。
4. **入り口は、1 つずつ別の単位で `Query` を通すようにする (MCP → CLI → TUI)。** 入り口に `*store.Store` は残る。書き込みのユースケースと `sync.Syncer` に渡すためで、組み立て (段階 d4) で消える。
5. **まだ入れないもの**: `TaskTags` は `asana.Ref` を返すので、d1 (`asana/model`) のあと、TUI の単位で入れる。`SyncState`・`SetSyncState` (TUI の画面の状態の保存) は、TUI の単位で形を決める。

## 理由

- `Query` が `QueryStore` を使うので、インターフェースは使う側 (app) にある (ADR 0003 の 2、ADR 0008)。
- 中身のない委譲だが、入り口の読み取りが store の型に頼らなくなる。組み立て (d4) で入り口から `*store.Store` をなくすとき、入り口は `app.Query` と書き込みのユースケースだけを受け取ればよい。
- 読み取りの手順で、入り口に重なっているもの (受信箱が使えないときに、最近変わったタスクを代わりに出す、など) は、あとで `Query` のメソッドにまとめられる。振る舞いを変えないため、この段階ではまとめない。

## 選ばなかった案

- **読み取りのインターフェースだけを app に置き、入り口が `*store.Store` をそのインターフェースとして持つ**: 使う側が入り口になり、ADR 0008 の考えと合わない。
- **入り口ごとにインターフェースを置く**: 3 つの入り口で、ほとんど同じものが 3 つできる。
- **領域ごとに `TaskQuery`・`ProjectQuery`・… と分ける**: 使う側が `Query` 1 つなので、分けても得るものがない。偽の store を作るテストが増えたら、そのとき分ける。
