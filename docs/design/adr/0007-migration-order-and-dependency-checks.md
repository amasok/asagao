# ADR 0007: アプリ層 → ドメイン → リポジトリ → ポートの順に移し、依存の向きは go list のテストで守る

- 状態: 提案 (Issue #69 の設計の段階)
- 日付: 2026-11-16

## 背景

- Issue #69 の案は、段階 a (アプリケーション層)、b (ドメイン層)、c (リポジトリ)、d (ポート) の順で、「順番は設計で決め直す」としていた。
- 新しい機能 (#28〜#36) は、段階 a が終わるまで待っている。
- 段階の間で、3 つの入り口と store と sync に同時に手が入る。決まりが口約束だと、移したあとにまた崩れる。

## 決めたこと

1. **順番は a → b → c → d のまま。** 理由:
   - a が最も効く: 重複 (作成 3 か所、変換の組 11 か所、期日 6 か所) が、機能を足すたびに増える。a が終われば機能の作業を始められる。
   - a は振る舞いを変えずに進めやすい: 入り口のテストが、そのまま「同じ振る舞い」の証拠になる。
   - b は a のあとのほうが楽: ユースケースが 1 か所になってから、そこから呼ぶドメインの関数を作れる。
   - c は b のあと: store から判断を出すには、出す先 (ドメイン) が要る。
   - d は最後: 型の移動 (`asana/model`) は import の書き換えが多く、ほかの段階とぶつかりやすい。ほかが落ち着いてから行う。
2. **段階 a の 2 つ目の PR (a2) で、依存の向きのテストを入れる。** 目標の形 (`architecture.md`) を表にし、今の違反は理由と直す段階を付けた許可リストに書く。許可リストにない新しい違反と、もう起きていない古い許可の両方で、テストが落ちる (ラチェット)。詳しくは `docs/design/dependency-rules.md`。
   - a1 より前に入れない理由: a1 で作る `internal/app` の位置づけを、テストの表に入れてから始めたいため。a1 は小さいので、その間に崩れる心配は少ない。
3. **どの PR も、仕様 (`openspec/specs/`) を変えない。** レビュー役は、`git diff main -- openspec/specs` が空であることを確かめる。
4. 各段階の PR の範囲は `docs/design/migration-plan.md` に書く。範囲を変えるときは、migration-plan.md を同じ PR で直す。

## 結果

- 段階 a は 6〜8 本ほどの PR になる。a1 だけで、CLI と MCP のタスク作成の重複がなくなる。
- 依存の向きのテストは、`go test ./...` の中で動き、CI のワークフローは変えない。
- 今の import は、すべて architecture.md の表で「許す」か「直す」に分けてある。「許す」は決まり (層と、入り口から使ってよい adapter) としてテストに書き、許可リストには入れない。段階 d が終わったとき、許可リスト (「直す」の行) が空になっていることが、#69 の終わりの条件の 1 つになる。

## 選ばなかった案

- **b (ドメイン) を先にする**: ドメインの関数を作っても、呼ぶ場所が 3 つの入り口と store に散らばったままで、重複が減らない。
- **依存の向きのテストを最後に入れる**: 移している間に崩れても気づかない。
- **golangci-lint の depguard を使う**: `dependency-rules.md` の「選ばなかった案」を参照。
