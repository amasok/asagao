# 書き込みの流れ (出来事の順)

1 つの書き込みが、利用者の入力から「確定」までに通る順番。振る舞いの細部は仕様 (`openspec/specs/write-flow`、`outbox-push`、`sync-pull`) にある。ここでは順番と、どこで何が決まるかだけを書く。

## 全体

```
 ① 入力を受ける        入り口 (TUI / CLI / MCP)
        │  期日の解釈 (dates.Parse)、名前の解決 (ResolveProject / ResolveSection / ResolveUser)、
        │  Markdown → rich text と plain の組 (richtext.Target)
        ▼
 ② ローカルに反映する   store.*Local の 1 つのトランザクション
 ③ outbox に積む        (②と③は同じトランザクション。どちらかだけにはならない)
        │  検証 → 今の値を読む → 畳み込み (未送信の作成へ / 既存の update へ / 元に戻ったら消す)
        │  → キャッシュの行を書き換える → 操作を保存 (または消す)
        ▼
 ④ 送る (push)          sync.Syncer.Push (CLI・MCP はすぐ、TUI は同期全体)
        │  push のロック → アカウントの確認 → 中断された操作を戻す → 積んだ順に 1 件ずつ
        │  → 送る前に操作を読み直す → (更新なら) Asana の今の値と比べて競合を見る → 送る
        ▼
 ⑤ 結果を記録する       store.Complete* / CompleteOp / Mark*
        │  作成の成功: gid の書き換え・送った記録・キャッシュの反映・操作の削除を 1 つのトランザクションで
        │  それ以外の成功: CompleteOp で操作を消し、キャッシュの反映はあとで別に (失敗してもよい)
        │  分からない: 自動確認中 (verify) にする
        │  届いていない: pending に戻す
        │  断られた: failed にする / 対象が消えていたら捨てた変更として記録する
        ▼
 ⑥ 照合する             Syncer.reconcile (自動確認中の作成だけ)
        │  Asana を探す → 1 件: 記録して完了 / 0 件: 待ってから再送 / 2 件以上: failed
        ▼
 ⑦ 確定する             取り込み (pull) で Asana の値がキャッシュに入る。
                        まだ未送信の操作があれば、取り込みの中で当て直す (reapply)
```

## 段ごとの決まり

### ① 入力を受ける (今は入り口ごと、段階 a で app 層に移す)

- 期日・名前・送り先の決め方は、今は入り口ごとに書かれていて、少しずつ違う (write-flow の仕様の「タスク作成の入力」「作成先と担当の決め方」「期日の解釈」)。
- 段階 a では、**違いをそのまま残して**ユースケースにまとめる。入り口ごとの違いは、ユースケースの引数 (例: 「担当の既定を自分にするか」) か、入り口の側の入力の集め方に残す。違いをなくすのは、振る舞いの変更なので別の Issue にする。

### ②③ ローカルに反映して outbox に積む (store)

- 反映と積むのは、必ず同じトランザクション (`Store.tx`)。この中でネットワークを使わない。push のロックも取らない (#50)。
- 判断の順番 (`UpdateTaskLocal`、internal/store/outbox.go:83-165):
  1. 欄の名前と型を確かめる (トランザクションの外、`validateFields`)。
  2. 今の値を読む。
  3. 承認の状態を確かめる。
  4. ローカル gid なら、一度も送っていない作成に畳み込んで終わる。作成が送信中・確認中・失敗なら、次へ。
  5. `pending` か `conflict` の一番新しい update を探す。なければ作る (base は今の値)。
  6. 欄ごとに base を 1 回だけ取り、base と同じなら外す。
  7. キャッシュの行を書き換える。
  8. 欄がなくなったら操作を消す。そうでなければ保存する。
- 4〜6 と 8 は、SQL を使わない純粋な判断で書ける (段階 b で、ドメインの関数 `outbox.Fold` のようにする候補)。

### ④ 送る (sync)

- 送るのは 1 つのプロセスだけ (push のロック)。同期全体もロックを持ったまま行う。
- アカウントが変わっていたら、何も送らない。
- 作成がまだのローカル gid に向けた操作は飛ばす。親が先、子があと。
- 同じ push の中で、同じ操作を照合するのは 1 回まで、1 つの操作に使う手順は 4 回まで。

### ⑤ 結果を記録する (store)

- 作成の成功の記録は、`Complete*` の 1 つのトランザクションで、操作の削除と一緒に行う。作成以外は `CompleteOp` で操作を消してから、キャッシュの反映を別に行う (失敗しても次の取り込みで直る)。
- どちらでも、操作の削除に失敗したとき (`sentNotSaved`) は自動確認中にする。作成は Asana を探して照合し、再送してよい操作はそのまま再送する。
- 送れたか分からないときに、利用者に聞かない。自動確認中にして、照合する (CLAUDE.md の「ユーザーに判断を押し付けない」)。

### ⑥ 照合する (sync)

- 照合は、作成 (再送してよくない操作) だけ。再送してよい操作は、そのまま再送する。
- 時刻は Asana の時計で比べる。PC の時計がずれていても、探す範囲がずれない。
- 決められないとき (候補が 2 件以上、探す場所がない) だけ、`failed` にして利用者に知らせる。

### ⑦ 確定する (sync の pull)

- 取り込みは Asana の値で行を書き、同じトランザクションで、`failed` 以外の未送信の操作を当て直す。だから、送る前に取り込みが来ても、ローカルの変更は消えない。
- 片付け (prune) は、outbox に操作があるタスクを消さない。

## 入り口ごとの違い (今)

| | TUI | CLI | MCP |
|---|---|---|---|
| ④ をいつ行うか | 書き込みのあと同期全体 (`Run`) | すぐ `Push` (20 秒) | すぐ `Push` (20 秒) |
| 送れたかの知らせ方 | 未送信の数と項目の印 | 文 / `--json` の `sent` | `sent` と `note` |
| 送らない形 | `--offline` | — | `--read-only` (書き込みのツールも出さない) |
| ロックが取れないとき | 5 秒から 1 分まで待って試し直す | 「別の asana-tui が送信中です」 | note で知らせる |

## 段階 a のあとの形

```
 入り口 ──▶ app.Tasks.Create(ctx, CreateTaskInput) ──▶ (①の解釈) ──▶ store.CreateTaskLocal (②③)
        ◀── gid / FieldError
 入り口 ──▶ 入り口ごとの送り方 (CLI・MCP: Push を 20 秒 / TUI: 同期を頼む)
        ◀── WriteResult{TaskGID, Sent, Push, Discarded} (CLI・MCP)
 入り口 ──▶ 結果を自分の形で表示する
```

- ④ をいつ・どう行うかは入り口ごとに違うので、ユースケースの中で決めない。ユースケースは ②③ までを行って gid を返し、**入り口が**送る。CLI と MCP は `Push` を 20 秒で呼んで結果を返し、TUI は同期を頼むだけで、送れたかは未送信の数で示す。`sent` の決め方 (CLI は未送信の数も見る、MCP は見ない) と `task_gid` の返し方 (CLI は送れたら空、MCP は本物の gid) も入り口ごとに違うので、送った結果から入り口が決める (write-flow の仕様、ADR 0006)。送り方のポート (`Sender`) は作らない (a3 で決めた。ADR 0006 の 2)。
