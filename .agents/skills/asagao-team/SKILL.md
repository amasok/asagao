# asagao-team (サブエージェント並列開発プロトコル)

精度を高めるために「実装」「攻撃テスト」「独立レビュー」を分離しつつ、**トークンを無駄に消費しない粒度**で並列化する。

## 分割・並列化の基準（分けすぎないルール）

- **3 名フル編成 (`coder` + `tester` + `reviewer`) の対象**:
  - `sync` / `store` / マイグレーション / 認証・セキュリティ / 複数層にまたがる設計変更に限定する。
- **1〜2 名にまとめるもの（分けすぎ禁止）**:
  - 1〜2 ファイルの修正、定数・色名・UI 文言追加などの小規模 Issue は `coder` 単独、または `coder` + `tester`（兼軽量レビュー）で完結させ、独立 `reviewer` を立てない。
  - 同一ファイル・同一マイグレーションを触る密結合タスク、単純な調査も 1 エージェントにまとめる。
- **並列化するもの・同時稼働上限（クォータ `429` / 5時間枠対策）**:
  - 変更ファイルやマイグレーション番号が衝突しない独立 Issue の並列、実装完了後の `asagao-tester` と `asagao-reviewer` の同時実行は有効だが、**同時稼働は最大 2 本を目安（上限 3 本）** とし、7〜9 体を短時間に集中起動しない。
- **先出し起動禁止**:
  - `asagao-tester` と `asagao-reviewer` は **必ず `asagao-coder` の実装コミット完了後に起動**する（実装前に待機起動しない）。
- **モデル階層化 (`invoke_subagent` の `Model` 指定)**:
  - `research`（コード探索・全体調査・棚卸し）→ `flash`（単純集計・一覧化は `flash_lite`）
  - `asagao-tester`（境界テスト作成・実行・mutation 確認）→ `flash` を基本（複雑な並行バグ再現のみ `inherit`）
  - `asagao-reviewer`（通常の差分レビュー）→ `flash` を基本（`sync` / `store` / マイグレーション / セキュリティ等の高リスク変更のみ `inherit` / `pro`）
  - `asagao-coder`（複雑な設計・複数パッケージ実装）→ `inherit`（1〜2 ファイルの単純修正は `flash`）
- **親エージェント (リーダー) の役割**:
  - 最初に最小限の調査をして対象ファイル・要件・制約を特定し、サブエージェントへピンポイントのブリーフを渡す（各サブエージェントに同じ探索を重複させない）。
  - 並行実装時はリーダーが `git worktree add .worktrees/<branch> -b <branch> main` をあらかじめ切り、サブエージェントは `Workspace: "inherit"` で専用ディレクトリを指定する（未追跡の `.worktrees/` があると `Workspace: "share"` が失敗するため）。
  - `asagao-reviewer` 起動前に `git diff main..<branch> > <scratch>/diff-<branch>.patch` と `git diff --stat main..<branch>` を生成し、**差分パッチパスと変更ファイル一覧（フルパス）** をブリーフに明記して渡す。
  - 途中経過はユーザーに中継せず、指摘の修正→再検証まで回しきってから最終報告する。

## 役割定義 (`define_subagent` 用テンプレート)

### 1. `asagao-coder` (実装担当 / `EnableWriteTools: true`)
- **責務**: 割り当てられた `.worktrees/<branch>` で要件の設計・実装・単体テストを行う。
- **ルール**:
  - `AGENTS.md` / `CLAUDE.md` の厳守事項（本物 Asana・`store.db` 禁止、`termsafe`、`archtest`）を守る。
  - 修正前なら失敗するテストを必ず追加する。
  - コミット前に必ず `gofmt -w` をかけ、`gofmt -l ./cmd ./internal` が空であることを確かめる (CI は gofmt を検査しない)。
  - 開発中の確認は変更パッケージ＋`-run '<Pattern>'` のみで回す。完了前も `go build ./... && go vet ./...` と **関連パッケージの `go test -race ./internal/<pkg>/...`** までとし、全パッケージの `go test -race ./...` は回さない。
  - `search_web` は最大 2〜3 回に絞り、まず既存コード・`openspec/`・既存テストを確認する。
  - `git add -A` 禁止、`push` 禁止。コミットメッセージ末尾には必ず `Co-Authored-By: Gemini (Antigravity) <noreply@google.com>` を付ける。
  - 完了報告は **10 行以内の箇条書き**（設計判断・変更ファイル・テスト結果・残課題のみ）に収める。

### 2. `asagao-tester` (攻撃テスト担当 / `EnableWriteTools: true`)
- **責務**: 実装完了後の `.worktrees/<branch>` に対し、壊しにいく側のテスト (`*_attack_test.go`) を書いて検証する。
- **観点**:
  - 境界値、異常応答 (`401`/`402`/`403`/`404`/`429`/`500`・空・破損 JSON・ネットワーク断)
  - 並行実行 (`-race`)、時刻経過・時計のズレ、大文字小文字・制御文字 (`termsafe`)、キャッシュ整合性、冪等性
- **ルール**:
  - 不具合を見つけたら実装を勝手に直さず、再現テストを残して「テスト名・入力・症状・原因箇所」をリーダー（または実装担当）へ返す。テストを `t.Skip` に逃げない。
  - 攻撃テストの作成・修正ループは `go test ./internal/<pkg>/ -run '<Pattern>'` で素早く回す。
  - 仕上げに必要なら `mutation` スキルでテスト強度を確認する。
  - 最終確認は単独ブランチなら `go vet ./... && go test -race ./...` を 1 回だけ回す。複数ブランチを `scripts/land.sh merge` でまとめて統合する場合は関連パッケージの `go test -race` までとし、全パッケージ `-race` は統合時の 1 回へ集約する。
  - テストファイルをコミットする際も、末尾に必ず `Co-Authored-By: Gemini (Antigravity) <noreply@google.com>` を付ける。
  - 完了報告は **10 行以内の箇条書き**（追加テスト・検出した不具合・テスト結果・mutation 結果のみ）に収める。

### 3. `asagao-reviewer` (レビュー担当 / `EnableWriteTools: false`)
- **責務**: 要件と差分を受け取り、先入観なく正しさ・安全性を精査する（コード編集は一切しない）。
- **観点**:
  1. 要件・エッジケースの網羅
  2. 4xx / 5xx / 429 / 401 / 402 / オフライン時にデータ消失・二重作成・同期停止・誤キャッシュが起きないか
  3. `termsafe` 通過と `archtest` 規約
  4. 並行実行安全性・マイグレーション後方互換性
  5. テストが本当に不具合を捕まえるか
- **ルール（ツール制約と重複防止）**:
  - `EnableWriteTools: false` では `run_command` が使えず `git diff` や `ls` を実行できない。最初にリーダーから渡された `<scratch>/diff-<branch>.patch` と変更ファイル一覧（フルパス）を `read_file` で読み、存在しないパスを推測で `read_file` し続けない（テストファイル見落としによる誤検知も防ぐ）。
  - 全パッケージの `go test -race ./...` は回さない（`tester` / `land.sh` と重複するため）。
- **出力**:
  - `high` (データ消失・安全性・重大バグ) / `medium` (要件漏れ・特定条件で壊れる) / `low` (軽微な改善) に分類し、ファイル・行番号・再現入力・修正案を簡潔な箇条書きで返す（長文のコード引用は避ける）。
  - `high` / `medium` が 0 件なら「承認 (LGTM)」と明記する。

## 標準フロー

1. **準備**: リーダーが対象 Issue の要件・衝突有無を確認し、独立ブランチ用に `.worktrees/<branch>` を切る。
2. **Phase 1 (実装・最大 2 本並列)**: 対象 Issue の `asagao-coder` を起動する。
3. **Phase 2 (検証・実装完了後に起動)**: 実装コミットが終わったブランチから順に `asagao-reviewer`（読取専用、差分パッチ必須）と `asagao-tester`（攻撃テスト追加）を起動する（小規模 Issue は省略・統合可）。
4. **Phase 3 (修正・再確認)**: `high` / `medium` 指摘やテスト失敗があれば `asagao-coder` に差し戻し、修正後に再確認する。
5. **Phase 4 (統合)**: 承認・テスト通過を確認したら、ユーザーの指示に応じて `land` スキルで取り込み・PR 作成を行う。

## トークン・5時間枠を溶かさない運用ルール

- **ポーリング禁止**: バックグラウンドコマンドやサブエージェントは完了通知（reactive wakeup）で自動再開するため、`manage_task(status)` を繰り返さずターンを終えて待つ。
- **並列バッチとまとめ読み**: 独立した `read_file` や読み取りコマンドは 1 ターンにまとめて並列呼び出しする。同一ファイルを 50〜100 行ずつ何度も読み直さず、先に grep 等で位置を特定して必要範囲を 1 回で読む。
- **親コンテキストの二乗肥大化 (`O(N²)`) を防ぐ**: 詳細ログや長い出力は `<scratch>/` に書き出してパスだけ親へ返す。PR や 1〜2 Issue の区切りごとに `/compact`（または新会話への切り替え）を行い、数百 KB まで膨らんだコンテキストのまま作業を続けない。
- **`Workspace: "share"` の罠を回避する**: `.worktrees/` 等の未追跡ディレクトリがあると `Workspace: "share"` が失敗してターンを浪費するため、リーダーが手動で `.worktrees/<branch>` を切って `Workspace: "inherit"` で渡す運用を標準とする。
